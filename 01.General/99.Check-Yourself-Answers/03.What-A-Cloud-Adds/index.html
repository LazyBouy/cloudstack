    Answers: What Does a Cloud Add to Virtual Machines?¶

    ← Back to the post

    1. Five KVM hosts and VMs on request by email: is that a cloud?¶

    No. It's virtualisation, done by hand.

    KVM and libvirt do run VMs, but each host's libvirt manages that host's VMs and nothing else. It starts a VM where it's asked; it never chooses a host. Someone still has to read each email, pick a host, log in and ask.

    Two things are missing, and they're the two traits of NIST's definition the article followed:

    • Self-service. A person sits between every request and every VM, so nothing happens at 2 a.m., and the queue grows with every new researcher.
    • A shared pool, handed out automatically. The hosts are there, but nothing places each VM where there's room, keeps track of whose VM is where, or stops one group taking everything.

    What would add them is software above the hosts: something that takes each request itself, picks a host, keeps the records and enforces the rules. NIST's own footnote says a cloud is hardware plus that software. In CloudStack, it's the management server.

    2. Self-service and a shared pool take the admin out of every request. What must the software do instead?¶

    Everything the admin used to do, with no person in the loop, at any hour:

    1. Hold each tenant to its share: check, for every new VM, that its tenant hasn't reached its limit.
    2. Pick a host with room: one with enough spare CPU and memory for the size asked for. The person asking chooses only a place; only the operators may name a host.
    3. Keep the records: whose each VM is, and which host it's on.
    4. Tell the chosen host to start the VM. On a KVM host, the instruction ends at that host's libvirt, the same libvirt the admin used by hand.
    5. Refuse requests that touch another tenant's VMs.

    That list is the management server's job description. Steps 2 to 4 even come in that order in the code: it picks the host, writes it into the VM's record, and only then sends the instruction (see the Evidence below).

    3. The cloud's only management server crashes at 3 a.m. What happens to the running VMs, and what can't anyone do?¶

    The running VMs carry on. CloudStack's docs say so even for the worst case, every copy of the management server down: "All Guest Instances will continue to work."

    Why? Because the management server isn't in the VMs' path. Each VM runs under its own host's hypervisor, which doesn't need the management server to keep it going. On a KVM host, CloudStack's own program there notices the connection has dropped, and simply keeps trying to reconnect. A VM's own work, such as serving a web page, never went through the management server in the first place.

    What stops is every request to the cloud. Nobody can create a VM, and the web interface doesn't answer. And if a host fails meanwhile, the automatic restarts that CloudStack can do for that host's VMs don't happen while it's down either.

    In the kitchen picture: HQ has closed for the night. The kitchens keep cooking the brands already open, but no new brand can launch until morning.

    4. What is a tenant, and can a physicist stop the Biology VM on the same host?¶

    A tenant is one of the customers that share a cloud, kept apart from the others: usually a group, such as a company or a department of a large organisation. It isn't the same thing as a person: it owns the VMs, and its people each log in as members of it. And it needn't pay: at the university, Physics and Biology are tenants, and they're departments.

    The physicist can't stop the Biology VM. Sharing a host is normal (it's what makes the pool a pool), but sharing a host isn't sharing VMs. Two guards stand between the tenants' VMs here (their networks are kept apart too):

    • On the host, the hypervisor keeps the two VMs apart, as it keeps every VM apart from its neighbours: strongly, though not absolutely.
    • At the management server, a request that names a VM is checked against that VM's owner. Physics doesn't own the Biology VM, so the request is refused.

    Why must tenants be kept apart at all? Because the pool is shared. Without the checks, any tenant could touch, or take, what's another's, and no tenant could trust the cloud. Tenants who need more than that can have hosts reserved for them alone, but that's an option the operators switch on, not the rule.

    5. Is CloudStack a hypervisor?¶

    No. CloudStack commands hypervisors; the hypervisor on each host runs the VMs.

    Its management server decides where each VM goes and sends the instruction. What happens next depends on the family:

    • On a KVM host, a small CloudStack program on the host hands the instruction to the host's libvirt, which starts the VM.
    • For the XenServer family (XenServer and XCP-ng), CloudStack talks to XAPI, the family's own management service.
    • For VMware, CloudStack talks to vCenter, which manages the ESXi hosts.

    Even in the smallest set-up, where one machine runs the management server and is also a KVM host, the management server stays a program of its own, separate from the hypervisor. And the VMs outlive the management server's outages: if it were their hypervisor, stopping it would stop them.

    Evidence¶

    The post states these facts in plain words. Here are the lines of CloudStack's code, and the passages of the docs, that back them. Code is quoted at the commit the post is written against.

    Each host's libvirt manages that host's VMs¶

    CloudStack's program on a KVM host connects to libvirt with a local address (LibvirtConnection.java, line 115):

    // cloudstack: plugins/hypervisors/kvm/src/main/java/com/cloud/hypervisor/kvm/resource/LibvirtConnection.java, line 115
return "qemu:///system";

    libvirt's Connection URIs page explains it: "qemu:///system connects to a system mode daemon", which "will handle qemu instances on behalf of all users of the machine (among other things)". An address with no host name in it is local: "Either the transport or the hostname must be given in order to distinguish this from a local URI." One libvirt, one machine.

    NIST's two traits, and what a cloud physically is¶

    NIST SP 800-145 (final text), section 2, on self-service:

    On-demand self-service. A consumer can unilaterally provision computing capabilities, such as server time and network storage, as needed automatically without requiring human interaction with each service provider.

    On the shared pool:

    Resource pooling. The provider's computing resources are pooled to serve multiple consumers using a multi-tenant model, with different physical and virtual resources dynamically assigned and reassigned according to consumer demand. There is a sense of location independence in that the customer generally has no control or knowledge over the exact location of the provided resources but may be able to specify location at a higher level of abstraction (e.g., country, state, or datacenter).

    Its footnote 2, on hardware plus software:

    A cloud infrastructure is the collection of hardware and software that enables the five essential characteristics of cloud computing. The cloud infrastructure can be viewed as containing both a physical layer and an abstraction layer. The physical layer consists of the hardware resources that are necessary to support the cloud services being provided, and typically includes server, storage and network components. The abstraction layer consists of the software deployed across the physical layer, which manifests the essential cloud characteristics. Conceptually the abstraction layer sits above the physical layer.

    And its example of the many consumers inside one organisation, from the same section: "The cloud infrastructure is provisioned for exclusive use by a single organization comprising multiple consumers (e.g., business units)."

    A tenant is a customer or a department; sharing hosts is the default¶

    CloudStack's docs (Accounts) describe CloudStack's record for a tenant, which it calls an account: "An Account typically represents a customer of the service provider or a department in a large organization."

    Hosts for one tenant alone are an option (Dedicating Resources to Accounts and Domains): "The root administrator can dedicate resources to a specific domain or Account that needs private infrastructure for additional security or performance guarantees." The root administrators are the cloud's operators. One of the kinds of dedication reads "A host will not be shared across multiple Accounts", which only needs saying because, without it, hosts are shared.

    A request on another tenant's VM is refused¶

    For a request that names a VM, the management server checks the caller against the VM's owner. Root admins pass, and so does the owner (DomainChecker.java, lines 234–243):

    // cloudstack: server/src/main/java/com/cloud/acl/DomainChecker.java, lines 234–243
protected void validateCallerHasAccessToEntityOwner(Account caller, ControlledEntity entity, AccessType accessType) {
    PermissionDeniedException exception = new PermissionDeniedException("Caller does not have permission to operate with provided resource.");

    if (_accountService.isRootAdmin(caller.getId())) {
        return;
    }

    if (caller.getId() == entity.getAccountId()) {
        return;
    }

    After two more rules, for administrators of part of the cloud and for shared projects (both taught later in the course), everyone else is refused (DomainChecker.java, lines 275–276):

    // cloudstack: server/src/main/java/com/cloud/acl/DomainChecker.java, lines 275–276

    XAPI and vCenter: the other families' own management software¶

    For the XenServer family, CloudStack's code calls XAPI (CitrixResourceBase.java, lines 185–186):

    The VMs keep running when the management server stops¶

    CloudStack's Concepts page (Massively Scalable Infrastructure Management): "Maintenance or other outages of the management server can occur without affecting the Instances running in the cloud."

    What stops, from the reliability page the post quotes (HA for Management Server): "When the Management Server is down, no new Instances can be created, and the end User and admin UI, API, dynamic load distribution, and HA will cease to work." The UI is the web interface; HA is the automatic restarts after a host fails. (The same section also calls the management server itself "stateless". That's too strong: each running copy also holds live connections to some of the hosts, as How Do You Ask CloudStack for Something? (coming soon) shows. Only its lasting records are kept elsewhere.)

    On a KVM host, the code agrees. When CloudStack's program on the host loses its connection, it runs its disconnect steps, logs the loss and tries to reconnect (Agent.java, lines 640–642):

    // cloudstack: agent/src/main/java/com/cloud/agent/Agent.java, lines 640–642
serverResource.disconnected();
logger.info("Lost connection to host: {}. Attempting reconnection while we still have {} commands in progress.", shell.getConnectedHost(), commandsInProgress.get());
stopAndCleanupConnection(true);

    It keeps redialling until a management server answers (Agent.java, lines 648–651):

    // cloudstack: agent/src/main/java/com/cloud/agent/Agent.java, lines 648–651
do {
    if (CollectionUtils.isEmpty(avoidMSHostList) || !avoidMSHostList.contains(host)) {
        connection = new NioClient(getAgentName(), host, shell.getPort(), shell.getWorkers(), shell.getSslHandshakeTimeout(), this);
        logger.info("Reconnecting to host: {}", host);

    On the way, the only thing it does is cancel a move that was in progress: a VM's to another host, or a disk's to other storage. Those are the only two disconnect steps in the code (LibvirtMigrateCommandWrapper.java, lines 247–249):

    // cloudstack: plugins/hypervisors/kvm/src/main/java/com/cloud/hypervisor/kvm/resource/wrapper/LibvirtMigrateCommandWrapper.java, lines 247–249
// add cancel hook before we start. If migration fails to start and hook is called, it's non-fatal
cancelHook = new MigrationCancelHook(dm);
libvirtComputingResource.addDisconnectHook(cancelHook);

    and (LibvirtMigrateVolumeCommandWrapper.java, lines 144–145):

    // cloudstack: plugins/hypervisors/kvm/src/main/java/com/cloud/hypervisor/kvm/resource/wrapper/LibvirtMigrateVolumeCommandWrapper.java, lines 144–145
cancelHook = new VolumeMigrationCancelHook(dm, destDiskLabel);
libvirtComputingResource.addDisconnectHook(cancelHook);

    Nothing on that path stops a running VM.
