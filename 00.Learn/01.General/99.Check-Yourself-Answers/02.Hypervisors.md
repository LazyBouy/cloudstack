# Answers: How Does a Hypervisor Work?

[← Back to the post](../02.Hypervisors.md)

## 1. Which part runs a VM's processors, which plays its devices, and which starts and stops it?

KVM runs the VM's processors. It's the part in the Linux kernel: it switches the real processor into guest mode to run one of the VM's virtual processors, and takes control back whenever the guest reaches for the real machine. With the processor's help, it also keeps each VM's memory separate.

Which virtual processor gets a real one at any moment? By default, the Linux kernel decides, just as it does for your programs.

QEMU plays the disk and the network card. Each running VM is one QEMU process, which presents the VM with devices its drivers recognise and does the real work with the host's own hardware.

libvirt starts and stops the VM. Its service, `libvirtd`, launches a VM's QEMU process, stops it, and keeps track of which VMs are running.

Why three parts? Each one does a different job. NIST splits any hypervisor platform the same way: a core for the processors and memory, pieces for the devices, and management pieces that start and stop VMs.

## 2. What happens when Ubuntu, inside a VM, sends data to its disk?

Step by step:

1. Ubuntu's kernel reaches for its disk. A disk is a device, something only the hypervisor may touch, so the processor stops the guest for a moment and hands control to KVM.
2. KVM passes the request on to the VM's QEMU process.
3. QEMU writes the data to the VM's disk on the host: a file, a device or storage reached over the network.
4. QEMU reports the write done to Ubuntu.

Why can't Ubuntu write to the real disk itself? Because it never sees it. It runs in guest mode, where the hypervisor stays in charge, and the disk its drivers talk to is a virtual one that QEMU plays.

That's the whole point of the arrangement. If every guest could command the real disk, three kernels would be giving orders to the same hardware, and nothing would keep the VMs apart.

## 3. What does hardware virtualisation spare the hypervisor, and what does it cost? Why does CloudStack refuse a KVM host without it?

It spares the rewriting. Without the processor's help, one way out is for the hypervisor to find the guests' instructions that touch the machine itself, and translate them in software. With it, the guest's own code runs straight on the processor, in guest mode, and the processor hands control to the hypervisor when it matters. Less code runs with full privileges, and an unchanged operating system runs with its usual drivers.

The cost is the hand-over itself: every switch to the hypervisor takes time, and NIST calls these switches the main cause of slowdown in a virtualised system. Only some operations cause one.

CloudStack refuses such a host because KVM can't run without it on Intel and AMD processors, and every VM CloudStack starts on a KVM host asks for KVM. CloudStack never falls back to running VMs with QEMU alone. So when a KVM host is added, CloudStack's setup on that machine checks that KVM can run there, and stops if it can't; on Ubuntu, the check is `kvm-ok` (see the Evidence below).

## 4. Whose process is the one `ps` shows per VM, and what does restarting `libvirtd` do to the VMs?

It's QEMU's. Each running VM is one QEMU process, which holds the VM's virtual devices and its memory, while KVM, in the kernel, runs its processors. That's exactly what CloudStack's own script looks for when it searches the process list for `qemu`.

If an admin restarts `libvirtd`, the VMs keep running. The manual says so: "Restarting libvirtd does not impact running guests."

That tells you where a VM really lives: in its QEMU process, with KVM's help. libvirt manages VMs; it doesn't run them.

## 5. Type 1 or type 2: ESXi, VirtualBox, Xen? And why is KVM hard to label?

ESXi is type 1: it's installed straight on the bare machine, with no ordinary operating system underneath.

Xen is type 1 too, in NIST's list (see the Evidence below). It's the hypervisor inside XenServer and XCP-ng.

VirtualBox is type 2: it's an application running on an ordinary operating system, like any other program on a laptop.

KVM is hard to label because it has something of both. It's part of the Linux kernel, which, with KVM loaded, becomes the hypervisor's core, right on the hardware, like type 1. But the machine is still an ordinary Linux system, where other programs can run beside the VMs and compete with them for the hardware, like type 2.

NIST says KVM has "features of both"; ShapeBlue calls it type 1. The safest answer describes it instead: a full Linux kernel turned hypervisor, with ordinary programs alongside.

And neither label is CloudStack's "hypervisor type", which is simply which hypervisor a host runs.

### A hypervisor platform is a core, device pieces and management pieces

NIST SP 800-125A Rev. 1, Executive Summary ([final text](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-125Ar1.pdf)):

> The core software used for server virtualization is called the Hypervisor which directly provides Central Processing Unit (CPU) and memory virtualization. […] Since the hypervisor by itself cannot provide all functions needed for server virtualization, it has supporting software modules (e.g., device drivers) for devices (e.g., Network and Storage devices) virtualization in addition to management modules for VM lifecycle operations and hypervisor configuration. The hypervisor together with these supporting modules and the hosting hardware constitute the hypervisor platform.

The same document, section 1, compares the hypervisor with an operating system: "Just as a conventional OS provides isolation between the various applications (or processes) running on a server, the hypervisor provides isolation between one or more VMs running on it."

### Guest mode, the hand-over, and what the processor's help spares

NIST SP 800-125A Rev. 1, section 4.1, on the two modes:

> Hardware extensions for Virtualization provide two modes of execution: host or root mode and guest or non-root mode. The host mode runs at a higher privilege than guest mode. The hypervisor code, which provides the baseline functionality HY-BF1 (processor allocation and memory management), runs in host mode while the guest OS and applications in VMs run in guest mode.

The post calls host mode "the processor's more powerful mode", and avoids the word "root", which means something else on Linux.

The same section, on what the help spares, and on memory:

> Additionally, when the hypervisor does not have to perform additional functions (e.g., translating sensitive instructions using techniques such as binary translation), the code executing with privileges is reduced in the hypervisor, making the TCB smaller and enabling better assurance verification.

> The consequence of this feature is that an unmodified Guest OS, along with their native device drivers, can be run in VMs.

> Memory Virtualization: Hardware-assisted memory virtualization is provided when the hardware enables the mapping of the Guest OS's physical addresses in their respective page tables to the host's physical addresses using hardware-based page tables instead of hypervisor-generated shadow page tables.

NISTIR 8221, section 3 ([final text](https://nvlpubs.nist.gov/nistpubs/ir/2019/NIST.IR.8221.pdf)), names the hand-over a "VM exit" and says only some operations cause one: "VM exits are a response to some instructions and events (e.g., page fault) from guest VMs and are the main cause of performance degradation in a virtualized system. These events could include external interrupts, accesses to control registers, task switches, and I/O operation instructions".

NISTIR 8221, section 2.1.2, says that on KVM "VMs run as normal Linux processes", which is why the kernel shares the processors among them like any other program. It also describes KVM this way: "the KVM module uses QEMU to create guest VMs running as separate user processes". Its Figure 2 draws one QEMU inside each VM. The VM's memory belongs to that process too. ### QEMU plays the devices, and asks KVM to run the processors

QEMU's manual on Ubuntu 24.04 ([qemu-system-x86_64](https://manpages.ubuntu.com/manpages/noble/man1/qemu-system-x86_64.1.html)) opens with "The QEMU PC System emulator simulates the following peripherals", a list that includes "2 PCI IDE interfaces with hard disk and CD-ROM support" and "PCI and ISA network adapters".

Ubuntu's docs ([VM tools in the Ubuntu space](https://ubuntu.com/server/docs/explanation/virtualisation/vm-tools-in-the-ubuntu-space/)) put the two parts together: "QEMU primarily functions as the user-space backend for KVM. When used in collaboration with KVM kernel components, it harnesses the hardware virtualization capability that KVM provides in order to efficiently virtualize guests."

QEMU is the one that asks. Its manual's `-accel` option: "This is used to enable an accelerator. Depending on the target architecture, kvm, xen, hvf, nvmm, whpx or tcg can be available. By default, tcg is used." (TCG is QEMU's own software emulator.) The kernel's [KVM documentation](https://docs.kernel.org/virt/kvm/api.html) describes the request QEMU makes for each virtual processor: "This ioctl is used to run a guest virtual cpu."

Without an accelerator, QEMU imitates the processor too. QEMU's own [docs](https://www.qemu.org/docs/master/system/introduction.html): "Note that the default is TCG, which is purely emulated, so you must specify an accelerator type to take advantage of hardware virtualization."

### Type 1, type 2, and KVM's place

NIST's ITL Bulletin for March 2018 ([PDF](https://csrc.nist.gov/CSRC/media/Publications/Shared/documents/itl-bulletin/itlbul2018-03.pdf)): "The hypervisor can be installed either directly on the hardware, or bare metal (Type 1 Hypervisor), or on top of a full-fledged conventional OS, called Host OS (Type 2 Hypervisor)."

NISTIR 8221, section 2.1:

> Type 1 hypervisors run directly on the host's hardware to control the hardware and manage guest operating systems (Guest OS). For this reason, Type 1 hypervisors are sometimes called bare metal hypervisors and include Xen, Microsoft Hyper-V, and VMware ESX/ESXi. Type 2 hypervisors are similar to other computer programs that run on an OS as a process. […] Some systems have features of both. For example, Linux's Kernel-based Virtual Machine (KVM) is a kernel module that effectively converts the host OS to a Type 1 hypervisor but is also categorized as a Type 2 hypervisor because Linux distributions are still general-purpose OSs with other applications competing for VM resources.

ShapeBlue ([Choosing the Right Hypervisor](https://www.shapeblue.com/choosing-the-right-hypervisor-apache-cloudstack-hypervisor-support/)): "Kernel-based Virtual Machine (KVM) is a Type 1 hypervisor integrated into the Linux kernel".
