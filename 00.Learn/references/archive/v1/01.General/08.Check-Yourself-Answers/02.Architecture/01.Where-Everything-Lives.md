# Answers: Where Does Everything Live?

[← Back to the post](../../02.Architecture/01.Where-Everything-Lives.md)

**1. Why are hosts grouped into clusters? Name three things that stop at a cluster's edge, and the one way the code lets a running VM cross it.**

A cluster is a wing of alike floors: "The hosts in a cluster all have identical hardware, run the same hypervisor, are on the same subnet, and access the same shared primary storage" ([About Clusters](https://docs.cloudstack.apache.org/en/4.22.1.1/conceptsandterminology/concepts.html#about-clusters)). "The same hypervisor" means the same type: each host runs its own. At the edge of a wing, these stop ([Clusters](../../02.Architecture/01.Where-Everything-Lives.md#clusters-wings-of-identical-floors)):

1. **The hypervisor.** A cluster has exactly one; `addCluster` requires it.
2. **Shared primary storage.** The usual storage room serves one cluster. Another cluster's VMs reach that data only through a copy via the warehouse.
3. **Live migration.** By default, a running VM moves only to another host of its cluster.
4. **The neighbourhood watch.** When a KVM host goes quiet, the head office asks the Up hosts of *its* cluster ([part 2](../../02.Architecture/02.Who-Calls-Whom.md#when-a-floor-goes-quiet)).
5. **System VM migration.** The docs: system VMs "can be migrated between hosts of the same cluster only" (VMware since 4.16 also within the pod) ([Migrating System VMs](https://docs.cloudstack.apache.org/en/4.22.1.1/adminguide/systemvm.html#migrating-system-vms)).

**The one way across:** when the hypervisor can move the disks too (storage migration), CloudStack widens its search for target hosts from the cluster to the whole pod. [The post](../../02.Architecture/01.Where-Everything-Lives.md#clusters-wings-of-identical-floors) shows `createDeploymentPlanForMigrationListing` under the hood: with storage migration, the plan has the pod but `null` for the cluster. The hosts it marks as suitable stay in the building.

You, as root admin, can name a host directly and go further with a user's VM, disks and all; only system VMs are held to their pod ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/server/src/main/java/com/cloud/vm/UserVmManagerImpl.java#L7986-L7991)):

```java
// cloudstack: server/src/main/java/com/cloud/vm/UserVmManagerImpl.java, lines 7986–7991

if (!VirtualMachine.Type.User.equals(vm.getType())) {
    // for System VMs check that the destination host is within the same pod
    if (srcHost.getPodId() != null && !srcHost.getPodId().equals(destinationHost.getPodId())) {
        throw new InvalidParameterValueException("Cannot migrate the VM, destination host is not in the same pod as current host of the VM");
    }
```

`!VirtualMachine.Type.User.equals(...)` means "anything but a user's VM": the same-pod rule is for system VMs only.

**2. A VM's disk sits in a floor's cupboard (local storage). What can't you do with it that you could with a VM in one of the wing's shared storage rooms, and why?**

**You can't move it to another floor while it runs, unless its disk moves too, and high availability won't restart it elsewhere.** Both come from one fact: no other floor can reach its disk.

**Why no other floor can reach it.** A cupboard has host scope, and the code counts host scope as "not shared" (`StoragePoolVO.isShared()`, under the hood in [Primary storage](../../02.Architecture/01.Where-Everything-Lives.md#primary-storage-three-sizes-of-storage-room)). The docs pair two facts about a wing: its hosts "access the same shared primary storage", and "Instances can be live-migrated from one host to another within the same cluster" ([About Clusters](https://docs.cloudstack.apache.org/en/4.22.1.1/conceptsandterminology/concepts.html#about-clusters)). A cupboard breaks the first, so it follows that live migration needs the disk to move too: the storage migration of answer 1.

**Why HA skips it.** When a host is found Down, high availability goes through its VMs, and passes over any whose root disk is on local storage ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/server/src/main/java/com/cloud/ha/HighAvailabilityManagerImpl.java#L388-L393)):

```java
// cloudstack: server/src/main/java/com/cloud/ha/HighAvailabilityManagerImpl.java, lines 388–393
for (VMInstanceVO vm : reorderedVMList) {
    if (_itMgr.isRootVolumeOnLocalStorage(vm.getId())) {
        if (logger.isDebugEnabled()){
            logger.debug("Skipping HA on Instance " + vm + ", because it uses local storage. Its fate is tied to the host.");
        }
        continue;
```

`continue` moves on to the next VM. The log line says why: "Its fate is tied to the host." With the floor gone, no other floor has the disk to start the room from.

A VM in one of the wing's shared storage rooms has neither problem: it can move to another floor of its wing while running, and, if its offering asks for HA, it's restarted on another floor when its host is found Down ([part 2](../../02.Architecture/02.Who-Calls-Whom.md#when-a-floor-goes-quiet)).

**So why use local storage at all?** When there's no shared storage to use. Edge zones, the lightweight zones of 4.18, rely on it: the pull request that added them lists "Use of local storage" among their features ([PR #6840](https://github.com/apache/cloudstack/pull/6840)). And system VMs use local storage only if you set `system.vm.use.local.storage` to `true` ([Hypervisor Support for Primary Storage](https://docs.cloudstack.apache.org/en/4.22.1.1/conceptsandterminology/choosing_deployment_architecture.html#hypervisor-support-for-primary-storage)).

**3. A customer asks for "their own rack". What can you give them, and what does CloudStack still decide?**

**You can give them the rack; you can't give them the choice of server.** This is [post 01's](../../01.Overview.md#check-yourself) "fast server in rack 3" again, answered properly.

A user of your cloud can't ask for a pod at all: "Pods are not visible to the end user" ([About Pods](https://docs.cloudstack.apache.org/en/4.22.1.1/conceptsandterminology/concepts.html#about-pods)). They pick a zone, and CloudStack picks the host ([post 01](../../01.Overview.md#why-your-users-pick-a-hotel-site-never-a-floor)).

But you, the operator, as a root admin, can dedicate a whole pod, a rack, to a domain or an account ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/plugins/dedicated-resources/src/main/java/org/apache/cloudstack/api/commands/DedicatePodCmd.java#L41-L43)):

```java
// cloudstack: plugins/dedicated-resources/src/main/java/org/apache/cloudstack/api/commands/DedicatePodCmd.java, lines 41–43
@APICommand(name = "dedicatePod", description = "Dedicates a Pod.", responseObject = DedicatePodResponse.class,
        requestHasSensitiveInfo = false, responseHasSensitiveInfo = false)
public class DedicatePodCmd extends BaseAsyncCmd {
```

`@APICommand(name = "dedicatePod", …)` declares the API command; `extends BaseAsyncCmd` makes it an asynchronous one, a work order. The same plugin has commands to dedicate a zone, a cluster or a host. The docs' "Private zones are reserved for a specific domain" is the zone case ([About Zones](https://docs.cloudstack.apache.org/en/4.22.1.1/conceptsandterminology/concepts.html#about-zones)).

So the customer gets rack 3. Their VMs go there when they're created with an *explicit-dedicated* affinity group ("To use an explicitly dedicated host, use the explicit-dedicated type of affinity group", [Dedicating Resources](https://docs.cloudstack.apache.org/en/4.22.1.1/adminguide/accounts.html#dedicating-resources-to-accounts-and-domains)), and CloudStack still picks the host inside the rack. Only you, as root admin, could name the host yourself ([post 01's answer 4](../../08.Check-Yourself-Answers/01.Overview.md)).

**4. Your head office's machine is running out of room, and you move the ledger to a third machine. What do you change, on which machine, and what happens to your floors?**

**First, move the data.** The ledger is two databases on one MySQL server: `cloud` and `cloud_usage`, the `db.cloud.name` and `db.usage.name` in `db.properties`. Copy both to MySQL on the new machine, and let it accept the head office on port 3306.

**Then, on the head office's machine, change two settings** in `db.properties`: `db.cloud.host` and `db.usage.host` now both name the new machine ([The head office's machine](../../02.Architecture/01.Where-Everything-Lives.md#the-head-offices-machine)). The head office opens both databases itself ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/client/conf/db.properties.in#L64-L70)):

```text
# cloudstack: client/conf/db.properties.in, lines 64–70
# usage database settings
db.usage.username=@DBUSER@
db.usage.password=@DBPW@
db.usage.host=@DBHOST@
db.usage.driver=@DBDRIVER@
db.usage.port=3306
db.usage.name=cloud_usage
```

`db.usage.host` takes the same `@DBHOST@` placeholder as `db.cloud.host`: at install time, both point at the same machine.

That's the install guide's usual shape for bigger clouds anyway: "For an installation that has multiple management server nodes, we assume the MySQL database also runs on a separate node" ([Install the database server](https://docs.cloudstack.apache.org/en/4.22.1.1/installguide/management-server/index.html)).

**You install nothing new on the head office's machine.** It never held the database server. Its Java program carries its own MySQL driver ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/client/pom.xml#L55-L58)):

```xml
<!-- cloudstack: client/pom.xml, lines 55–58 -->
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
</dependency>
```

The `mysql-client | mariadb-client` its package pulls in is only a command-line tool.

**Your floors don't notice.** The attendant's notebook, `agent.properties`, holds the head office's address and port and nothing about the ledger ([part 2](../../02.Architecture/02.Who-Calls-Whom.md#hiring-an-attendant-the-engineers-one-visit), under the hood), and the agent's code opens no database connection at all. The attendant talks only to the head office, on the staff line, and the head office reads and writes the ledger. [Part 2's map](../../02.Architecture/02.Who-Calls-Whom.md#who-talks-to-whom-the-whole-map) shows it: the only arrow into the ledger comes from the head office.

And if you later add a second head office, it points at the same `db.cloud.host` and `db.usage.host`: several head offices share one ledger ([part 2](../../02.Architecture/02.Who-Calls-Whom.md#growing-more-head-offices)).
