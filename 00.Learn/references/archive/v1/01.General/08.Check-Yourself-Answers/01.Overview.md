# Answers: What Is CloudStack?

[← Back to the post](../01.Overview.md)

**1. Twenty KVM servers, VMs created by your team on request: is that a cloud?**

Not yet. Go through NIST's five traits:

- **Self-service:** no. A human handles every request, and that's the most important failure.
- **Reachable over the network:** only in part. Users can SSH into a VM once it exists, but getting one means emailing a person, not calling a service.
- **A shared pool:** only in part. Everyone shares the twenty servers, but your team picks each VM's server by hand.
- **Elastic:** no. Growing and shrinking waits for your team.
- **Measured:** probably not. Nobody tracks who uses what.

KVM gives you the magic trick, virtualization; what's missing is the coordinating layer that turns it into a cloud. CloudStack's README lists the whole stack it brings, in one product ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/README.md?plain=1#L57-L67)):

**2. The management server crashes at 3 a.m. What happens?**

Your users' VMs that are already running **keep running**. They run on the hosts, under the hypervisor (KVM in our lab), not inside the management server. The management server only decides and sends instructions. CloudStack's own documentation says so: "Maintenance or other outages of the management server can occur without affecting the Instances running in the cloud" ([Concepts and Terminology](https://docs.cloudstack.apache.org/en/4.22.1.1/conceptsandterminology/concepts.html)).

What nobody can do is use the front desk. The web UI, CloudMonkey and the API all talk to the management server, so until it's back:

- no new VMs, and no starting, stopping or changing existing ones through CloudStack,
- no new accounts, networks or settings,
- no answers to "what's running where?", because that question goes through the API too.

In hotel terms: the head office closes for the night. The guests sleep on in their rooms, but nobody can check in, check out or change rooms until it reopens.

This is where the docs' "multi-node installation where the servers are load balanced" helps: with several identical management servers sharing one ledger, one machine stopping needn't close the whole front desk. Your lab will run just one.

**4. "The fast server in rack 3": what can the user choose, and who could grant it?**

**The user can choose a zone, the hotel site, never a host. Only a root admin, you, could grant "rack 3".**

The zone is compulsory for everyone ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/api/src/main/java/org/apache/cloudstack/api/command/user/vm/BaseDeployVMCmd.java#L79-L80)):

```java

@Parameter(name = ApiConstants.ZONE_ID, type = CommandType.UUID, entityType = ZoneResponse.class, required = true, description = "availability zone for the virtual machine")
```

`required = true` makes it compulsory; `type = CommandType.UUID` means it takes an ID, not a name.

The `hostid` parameter exists too, but its description says "parameter available for root admin only" ([the post shows it](../01.Overview.md#why-your-users-pick-a-hotel-site-never-a-floor)), and the code enforces it. When a request names a host, CloudStack checks who's asking ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/server/src/main/java/com/cloud/vm/UserVmManagerImpl.java#L6267-L6273)):

If a host was named (`hostId != null`) by someone who isn't a root admin, the request fails with "Parameter hostid can only be specified by a Root Admin, permission denied". (The `quickRestore` part covers a special case outside this post's scope.)

It isn't a missing feature; it's the definition of a cloud at work. NIST's "shared pool" trait says the customer "has no control or knowledge over the exact location of the provided resources but may be able to specify location at a higher level of abstraction (e.g., country, state, or datacenter)". CloudStack's higher level is the zone, which really is a data centre: zones are stored in the `data_center` table. The docs add that hosts "are not visible to the end user. An end user cannot determine which host their guest has been assigned to" ([Concepts and Terminology](https://docs.cloudstack.apache.org/en/4.22.1.1/conceptsandterminology/concepts.html)).

Keeping placement in the head office's hands also makes sense for the hotel as a whole (our reading, not a documented reason): only the head office sees every floor at once, so only it can tell where there's room. Who picks the host, and how, is the story of [How It Unfolds](../04.How-It-Unfolds.md) *(coming soon)*.

**5. Decode 4.22.1.1. Why does the code say 24.0.0-SNAPSHOT? Does 24 break the API?**

**4.22.1.1** reads, part by part:

- `4`: never changed since the first Apache release,
- `22`: the release,
- `1`: the first maintenance (bug-fix) release of 22,
- `1`: the first security release on top of 4.22.1.

CloudStack's own code describes the same four-part format, and the new three-part one ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/utils/src/main/java/org/apache/cloudstack/utils/CloudStackVersion.java#L81-L91)):

```java
// cloudstack: utils/src/main/java/org/apache/cloudstack/utils/CloudStackVersion.java, lines 81–91
* Parses a <code>String</code> representation of a version that conforms one of the following
* formats into a <code>CloudStackVersion</code> instance:
* <ul>
*     <li><code>&lt;major&gt;.&lt;minor&gt;.&lt;patch&gt;</code> (legacy, deprecated since 24.0.0, allowed only below major version 24)</li>
*     <li><code>&lt;major&gt;.&lt;minor&gt;.&lt;patch&gt;.&lt;security&gt;</code> (legacy, deprecated since 24.0.0, allowed only below major version 24)</li>
*     <li><code>&lt;major&gt;.&lt;minor&gt;.&lt;security release&gt;</code> (for versions &gt;= 24.0.0)</li>
* </ul>
*
* Legacy patch-based formats remain supported for backward compatibility, e.g. <code>4.23.0.1-SNAPSHOT</code>,
* but only below major version 24: a 4-position value whose major release is at or above 24, e.g.
* <code>24.0.0.1</code>, is rejected.
```

This is a comment written in HTML, where `&lt;` and `&gt;` stand for `<` and `>`. Read without them: the old format is `major.minor.patch.security`, as in 4.22.1.1, and from 24.0.0 on it's `major.minor.security release`.

**Why the code says 24.0.0-SNAPSHOT.** The course reads the newest development code, which is on its way to the next LTS release. In August 2026 the community voted to drop the meaningless "4.", so the release after 4.23 is 24.0.0, and `SNAPSHOT` marks it as not yet released. The database upgrade for that step already exists ([code](https://github.com/apache/cloudstack/blob/1a48a87587c03472feefb081cfac71b2ebd0f407/engine/schema/src/main/java/com/cloud/upgrade/dao/Upgrade42300to2400.java#L19-L30)):

**Does 24 break the API?** No, or at least not because of the number. It's a new label for the same kind of release.
