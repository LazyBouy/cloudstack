The module answers the course map's question for it: **what is CloudStack, and what happens when someone asks it for a VM?** It's planned from CloudStack's own shape (one deciding program, a modelled data centre, agents that dial in, storage that decides where a VM can go, VMs of its own), not from any other course.

## 1. The learner

- **Arrives knowing:** basic Linux only: the shell, files and permissions, installing packages, starting services with systemd, SSH, editing a config file. Not virtualisation, clouds, networking beyond "a machine has an IP address", storage protocols, databases or Java. Docker is needed only for the simulator lab, and that article says so.
- **Leaves able to:**
    1. Explain what a VM and a hypervisor are, what a cloud adds on top of them (self-service from a shared pool, for many tenants), and why that needs one deciding program. (01, 02)
    2. Name CloudStack's parts (management server, database, API, agent, hosts, primary and secondary storage, system VMs, virtual router) and say what each is for and where it runs. (03, 05, 06, 09, 10, 11)
    3. Explain why where a VM's disk lives, and how hosts are grouped (cluster, pod, zone), decide where a VM can run, move and restart; and correct the two classic wrong sentences: "a cluster runs one hypervisor" and "shared storage means VMs share disks". (06, 07, 08)
    4. Say who may ask the cloud for what: accounts, users, domains and roles, and what an ordinary user can and can't choose. (04, 08)
    5. Follow one `deployVirtualMachine` request step by step, from the API to a running VM, naming the part at each step. (12)
    6. Run a simulated cloud, then build a one-machine KVM cloud on Ubuntu from the 4.22 docs, and find each part of this module in it. (13, 14, 15)

## 3. Learning path

**How the path is shaped.** Two foundation articles (what a VM is; what a cloud adds) lead into the people's side of CloudStack (how you ask, and who may), then the machines' side, link by link (how hosts are reached, where disks live, how hosts are grouped, where disks come from, CloudStack's own VMs, networks). One journey article then crosses both sides, and the lab and the exercises close the module. The module README may present it in those stretches: 01–02, 03–04, 05–11, 12, 13–15, 16.

**A running example (optional, §7 decision 3).** A university's IT team runs a private CloudStack cloud for its researchers. The physics department is one of its tenants, and a researcher there wants a small Ubuntu VM, `web-01`. The threads below use it; the names are plain and never need to be remembered.

### The first-principles chains

**Chain 1: why a cloud needs one deciding program.**

1. A VM is a complete computer made of software. (01)
2. A hypervisor on each host shares out its hardware among VMs and keeps them apart; every host runs its own. (01)
3. By hand, an admin creates VMs on a host. (01, 02)
4. Many hosts and many tenants need someone to pick a host, keep the records and keep tenants apart, with no person in the loop: a cloud. (02)
5. Hence one program, the management server, which commands the hypervisors (02), takes every request through its API and keeps every fact in one database (03), and decides who may ask for what (04).

**Chain 2: reaching the hosts.**

1. The management server decides; each host's hypervisor runs the VMs. (02)
2. Instructions must reach each host, and CloudStack must know which hosts are alive. (05)
3. On KVM, an agent on the host opens a connection to the management server and keeps it open. (05)
4. Instructions come down that line; reports go up it every minute. (05)
5. Silence means trouble: CloudStack checks the host, and if it's down, restarts the HA-enabled VMs elsewhere. (05) For VMware and XenServer there's no agent: the management server reaches the hypervisor's own manager. (05)

**Chain 3: storage** (the one the first attempt broke).

1. A VM's disk is a file or a block device, somewhere. (06)
2. It can live on the host's own disk, or on a storage server reached over the network. (06)
3. A VM must be able to run on another host when it's moved, or when its host dies. (05 for the death and HA; 06 for the disk's part)
4. So other hosts must reach its disk: shared storage, which shares the place and never the disks. (06)
5. Hence storage that only one host reaches (local, 06, named as a scope in 07), storage the hosts of one cluster share (07), and storage the hosts of a whole zone share (08).

**Chain 4: grouping the hosts.**

1. Hosts that can take over each other's running VMs need the same hypervisor type and the same storage. (07)
2. Hence the cluster, and live migration within it. (07)
3. Racks of hosts share a switch and an address range: the pod. (08)
4. Data centres give isolation and redundancy, and give users a place to choose without choosing a host: the zone. (08)

**Chain 5: making a new VM's disk.**

1. A new VM needs an operating system on its disk. (09)
2. Installing one by hand for every VM is slow, so VMs start from a ready-made image: the template. (09)
3. Templates must be kept where every cluster of the zone can fetch them, apart from running disks: secondary storage. (09)
4. Running disks live on primary storage, so a template is copied to a pool the first time it's used there, and root volumes are made from the copy. (09)
5. Something inside the zone must download images and copy them around: the secondary storage VM, a VM CloudStack runs itself. (10)

**Chain 6: who may ask.**

1. Many tenants share one cloud. (02)
2. Every request comes through the API. (03)
3. So CloudStack must know who's asking and what they own: the account owns, the user logs in. (04)
4. Organisations nest, and admins look after their own part: domains and domain admins. (04)
5. What each one may do: the role, from root admin to user. (04)

**Chain 7: a VM's network.**

1. A VM needs an address and a way to reach others. (11)
2. Tenants mustn't see each other's traffic: each account gets its own guest network. (11)
3. Someone must hand out addresses and names and give a way out: the virtual router (11), a system VM (10).
4. The way out is the network's public IP address, shared by its VMs. (11)

**Chain 8: the lab's network** (added 2026-10-01).

1. A VM reaches the network through its host. (01, 11)
2. On KVM, a Linux bridge inside the host joins the host's network card and its VMs, system VMs included. (14)
3. CloudStack must know which kind of traffic goes where: traffic types, mapped onto the host's bridges by name. (14)
4. In the one-machine lab, management, public and guest traffic share one bridge, `cloudbr0`: the wizard's defaults leave the labels empty, and the code then uses `cloudbr0` for all three (GEN-61's evidence). (14 says it; 15's wizard does it)

**Chain 9: why the system VMs can start** (added 2026-10-01).

1. System VMs are VMs CloudStack runs for itself, on ordinary hosts. (10)
2. A VM's root disk is made from an image kept in the zone's secondary storage. (09)
3. So system VMs need an image of their own there: the system VM template. (15)
4. In 4.22 it ships inside the management server's package, and CloudStack copies it into the zone's first NFS secondary storage when that storage is added. (15)
5. With a host Up, primary storage ready and the template in place, CloudStack starts the SSVM and the CPVM. (15; v1 A-F81, to re-verify at the tag)

**The capstone.** Chain 1 + 6 (the request and its checks) → 3 + 4 (where it can go) → 5 (its disk) → 7 (its network) → 2 (the start instruction): article 12 walks them in that order.
