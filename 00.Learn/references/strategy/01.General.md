The module answers the course map's question for it: **what is CloudStack, and what happens when someone asks it for a VM?** It's planned from CloudStack's own shape (one deciding program, a modelled data centre, agents that dial in, storage that decides where a VM can go, VMs of its own), not from any other course.

## 1. The learner

- **Arrives knowing:** basic Linux only: the shell, files and permissions, installing packages, starting services with systemd, SSH, editing a config file. Not virtualisation, clouds, networking beyond "a machine has an IP address", storage protocols, databases or Java. Docker is needed only for the simulator lab, and that article says so.
- **Leaves able to:**
    1. Explain what a VM is; what a hypervisor is made of on a KVM host (the processor's help, the kernel's KVM, one QEMU process per VM, libvirt) and how type 1 and type 2 hypervisors differ; what a cloud adds on top (self-service from a shared pool, for many tenants); and why that needs one deciding program. (01, 02, 03)
    2. Name CloudStack's parts (management server, database, API, agent, hosts, primary and secondary storage, system VMs, virtual router) and say what each is for and where it runs. (04, 06, 07, 10, 11, 12)
    3. Explain why where a VM's disk lives, and how hosts are grouped (cluster, pod, zone), decide where a VM can run, move and restart; and correct the two classic wrong sentences: "a cluster runs one hypervisor" and "shared storage means VMs share disks". (07, 08, 09)
    4. Say who may ask the cloud for what: accounts, users, domains and roles, and what an ordinary user can and can't choose. (05, 09)
    5. Follow one `deployVirtualMachine` request step by step, from the API to a running VM, naming the part at each step. (13)
    6. Run a simulated cloud, then build a one-machine KVM cloud on Ubuntu from the 4.22 docs, and find each part of this module in it. (14, 15, 16)

### 02.Hypervisors: How Does a Hypervisor Work?

- **Status:** approved 2026-10-02 (new, at the user's request: §6)
- **Level:** Beginner · **Type:** Concept
- **The learner's question:** "01 said a hypervisor shares out the hardware and keeps VMs apart, and that on KVM each VM shows up as one process. But how can one processor run several operating systems, each sure it owns the machine? What is that one process? And is every hypervisor built like KVM?"
- **The one idea:** A hypervisor is a few parts with separate jobs: the processor's hardware virtualisation runs each VM's own code directly and hands control back whenever the VM reaches for the real machine; on a KVM host, the kernel's KVM runs the VMs' processors and, with the processor's help, keeps each VM's memory separate, one QEMU process per VM plays its devices, and libvirt starts and stops the VMs, while other hypervisors sit straight on the bare machine (type 1, like ESXi) or run as an app on another operating system (type 2, like VirtualBox).
- **Scope in:**
    - GEN-64 hardware virtualisation, the problem first: each VM's operating system expects to command the hardware itself, and several can't all do so on one machine. ### The first-principles chains

**Chain 1: why a cloud needs one deciding program.**

1. A VM is a complete computer made of software. (01)
2. A hypervisor on each host shares out its hardware among VMs and keeps them apart; every host runs its own. (01) On a KVM host it's the processor's help, the kernel's KVM, one QEMU process per VM, and libvirt to start and stop them. (02)
3. By hand, an admin asks each host's libvirt for VMs. (02, 03)
4. Many hosts and many tenants need someone to pick a host, keep the records and keep tenants apart, with no person in the loop: a cloud. (03)
5. Hence one program, the management server, which commands the hypervisors (03), takes every request through its API and keeps every fact in one database (04), and decides who may ask for what (05).

**Chain 2: reaching the hosts.**

1. The management server decides; each host's hypervisor runs the VMs. (03)
2. Instructions must reach each host, and CloudStack must know which hosts are alive. (06)
3. On KVM, an agent on the host opens a connection to the management server and keeps it open. (06)
4. Instructions come down that line, and the agent carries them out through libvirt (02); reports go up it every minute. (06)
5. Silence means trouble: CloudStack checks the host, and if it's down, restarts the HA-enabled VMs elsewhere. (06) For VMware and XenServer, type 1 hypervisors (02), there's no agent: the management server reaches the hypervisor's own manager. (06)

**Chain 3: storage** (the one the first attempt broke).

1. A VM's disk is a file or a block device, somewhere. (07)
2. It can live on the host's own disk, or on a storage server reached over the network. (07)
3. A VM must be able to run on another host when it's moved, or when its host dies. (06 for the death and HA; 07 for the disk's part)
4. So other hosts must reach its disk: shared storage, which shares the place and never the disks. (07)
5. Hence storage that only one host reaches (local, 07, named as a scope in 08), storage the hosts of one cluster share (08), and storage the hosts of a whole zone share (09).

**Chain 4: grouping the hosts.**

1. Hosts that can take over each other's running VMs need the same hypervisor type and the same storage. (08)
2. Hence the cluster, and live migration within it. (08)
3. Racks of hosts share a switch and an address range: the pod. (09)
4. Data centres give isolation and redundancy, and give users a place to choose without choosing a host: the zone. (09)

**Chain 5: making a new VM's disk.**

1. A new VM needs an operating system on its disk. (10)
2. Installing one by hand for every VM is slow, so VMs start from a ready-made image: the template. (10)
3. Templates must be kept where every cluster of the zone can fetch them, apart from running disks: secondary storage. (10)
4. Running disks live on primary storage, so a template is copied to a pool the first time it's used there, and root volumes are made from the copy. (10)
5. Something inside the zone must download images and copy them around: the secondary storage VM, a VM CloudStack runs itself. (11)

**Chain 6: who may ask.**

1. Many tenants share one cloud. (03)
2. Every request comes through the API. (04)
3. So CloudStack must know who's asking and what they own: the account owns, the user logs in. (05)
4. Organisations nest, and admins look after their own part: domains and domain admins. (05)
5. What each one may do: the role, from root admin to user. (05)

**Chain 7: a VM's network.**

1. A VM needs an address and a way to reach others. (12)
2. Tenants mustn't see each other's traffic: each account gets its own guest network. (12)
3. Someone must hand out addresses and names and give a way out: the virtual router (12), a system VM (11).
4. The way out is the network's public IP address, shared by its VMs. (12)

**Chain 8: the lab's network** (added 2026-10-01).

1. A VM reaches the network through its host. (01, 12)
2. On KVM, a Linux bridge inside the host joins the host's network card and its VMs, system VMs included. (15)
3. CloudStack must know which kind of traffic goes where: traffic types, mapped onto the host's bridges by name. (15)
4. In the one-machine lab, management, public and guest traffic share one bridge, `cloudbr0`: the wizard's defaults leave the labels empty, and the code then uses `cloudbr0` for all three (GEN-61's evidence). (15 says it; 16's wizard does it)

**Chain 9: why the system VMs can start** (added 2026-10-01).

1. System VMs are VMs CloudStack runs for itself, on ordinary hosts. (11)
2. A VM's root disk is made from an image kept in the zone's secondary storage. (10)
3. So system VMs need an image of their own there: the system VM template. (16)
4. In 4.22 it ships inside the management server's package, and CloudStack copies it into the zone's first NFS secondary storage when that storage is added. (16)
5. With a host Up, primary storage ready and the template in place, CloudStack starts the SSVM and the CPVM. (16; v1 A-F81, to re-verify at the tag)

**Chain 10: how one machine runs several operating systems** (added 2026-10-02).

1. Each VM brings its own operating system, which expects to command the hardware itself. (01)
2. Several of them share one machine, so something must stay in charge of the real hardware: the hypervisor. (01)
3. The processor helps: each VM's code runs directly, in a restricted guest mode, and the processor hands control to the hypervisor whenever a VM reaches for the real machine. (02)
4. On a KVM host, the kernel's KVM runs the VMs' processors and, with the processor's help, keeps each VM's memory separate, and one QEMU process per VM plays its devices. (02)
5. Something must keep each VM's description, and start and stop VMs on request: libvirt, which people and programs talk to (CloudStack's agent: 06). (02)
6. Other hypervisors place the same jobs differently: on the bare machine (type 1) or in an app on another operating system (type 2). KVM, inside a full Linux kernel, has features of both. (02)

**The capstone.** Chain 1 + 6 (the request and its checks) → 3 + 4 (where it can go) → 5 (its disk) → 7 (its network) → 2 and 10 (the start instruction, down to libvirt and QEMU): article 13 walks them in that order.
